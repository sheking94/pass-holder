# Synchronizacja P2P, plan 1 z 4: spike transportu i rdzeń w `core/` — plan implementacji

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Potwierdzić, że wtyczka MV3 może rozmawiać po HTTP z adresem w sieci lokalnej, a potem zbudować
w `core/` referencyjną implementację nowej synchronizacji: HLC, epoka, CPace, Noise KK i warstwa
transportu, przetestowaną na wektorach, które w planie 2 odtworzy Kotlin.

**Architecture:** Nowy kod trafia do `core/src/p2p/` i jest eksportowany jako przestrzeń nazw `p2p`, obok
dzisiejszego v1. Kod v1 (`sync.ts`, `protocol.ts`, serwer, obecni klienci) zostaje nietknięty, żeby repo
działało do planu 4, który usunie Pi. Logika serwera `processSync` jest używana ponownie przez hosta P2P,
bo bloby są dla niej nieprzezroczyste; nowa jest tylko warstwa epoki i transport.

**Tech Stack:** TypeScript 7, vitest 5, `@noble/hashes` 2.4 (jest), `@noble/curves` 2.x (nowa zależność:
ristretto255 i X25519), WebCrypto AES-GCM (jak w `cipher.ts`).

**Spec:** `docs/SYNCHRONIZACJA_P2P.md` (sekcje 2, 4, 5, 8 krok 0–1, 9).

**Pozostałe plany (osobne dokumenty, pisane po zakończeniu tego):**
2. Android `core`: port modułów z tego planu do Kotlina na tych samych wektorach, host synchronizacji.
3. Android `app` i wtyczka: tryb „Synchronizacja”, parowanie, „Urządzenia”, „Odtwórz z wtyczki”, nowy transport we wtyczce.
4. Usunięcie `server/`, `deploy/`, kodu v1 w `core/` i części `INSTALACJA.md` o Pi.

## Global Constraints

- Po każdym tasku `npm test` i `npm run typecheck` w katalogu głównym repo przechodzą (wszystkie workspace'y).
- Nie zmieniać plików v1: `core/src/sync.ts`, `core/src/protocol.ts`, `core/src/vault.ts`, `server/`, `extension/`, `android/`.
- Nowe AAD i etykiety zaczynają się od `passholder/v2/`.

- HLC: `{ ms, c, d }`, porównanie leksykograficzne `(ms, c, d)`, `d` to `deviceId`.
- Binaria na drucie jako standardowe Base64 z dopełnieniem (`toBase64` / `fromBase64` z `core/src/encoding.ts`).

Zasady (spec 4.3, 4.4, 5.1–5.3):
- `processP2pSync`: gdy `request.epoch !== epoch`, zwraca `{ epoch, currentRevision: store.currentRevision(), accepted: [], conflicts: [], changes: [], addresses }` **bez** wywołania `processSync`. W przeciwnym razie wynik `processSync` plus `epoch` i `addresses`.
- `syncVaultV2`: jeśli `vault.epoch === null`, pierwsze żądanie idzie z epoką pustym stringiem i służy tylko do jej poznania. Gdy `response.epoch !== vault.epoch`: ustaw `vault.epoch = response.epoch`, `lastSyncRevision = 0`, każdy wpis i nagrobek `revision = 0, dirty = true`, zignoruj resztę odpowiedzi, wykonaj kolejną rundę (nie liczy się do `maxRounds`; maksymalnie jedna zmiana epoki na wywołanie, druga rzuca `Error("Epoch changed twice during sync")`).
- Rozstrzyganie: lokalny `dirty` wygrywa, gdy `compareHlc(local.data.hlc, remote.data.hlc) > 0`. Przed porównaniem `clock.observe(remote.data.hlc)` dla każdego zdalnego rekordu.
- `addresses` z odpowiedzi dopisywane do `vault.addresses` bez duplikatów, w kolejności pojawienia się.

**Files:**

**Interfaces:**
- Produces:

  - `class CipherState { encrypt(ad: Uint8Array, plaintext: Uint8Array): Promise<Uint8Array>; decrypt(ad: Uint8Array, ciphertext: Uint8Array): Promise<Uint8Array> }`
  - `class NoiseKK { static initiator(o: { s: KeyPair; rs: Uint8Array; prologue: Uint8Array; e?: KeyPair }): NoiseKK; static responder(o: same): NoiseKK; writeMessage(payload: Uint8Array): Promise<Uint8Array>; readMessage(message: Uint8Array): Promise<Uint8Array>; split(): { send: CipherState; recv: CipherState }; get handshakeHash(): Uint8Array }`
  - Stała: `P2P_PROLOGUE = utf8("passholder/v2/noise")`.

Zgodnie z Noise rev. 34: wzorzec KK (`-> s`, `<- s` jako wiadomości wstępne; `-> e, es, ss`; `<- e, ee, se`), HASH SHA-256, HKDF przez HMAC-SHA256 z `@noble/hashes`, AES-256-GCM przez WebCrypto z nonce = 4 bajty zerowe + 8 bajtów licznika big-endian. Licznik 2⁶⁴−1 → błąd. `split()` dozwolony dopiero po dwóch wiadomościach; `send`/`recv` zależą od roli. Maksymalna długość wiadomości 65535 B (rzuć błąd powyżej).
