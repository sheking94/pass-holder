# V3 krok 1: rdzeń formatu wpisów v3 (TS + Kotlin) – plan wykonania

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Cel:** wpisy w formacie v3 (5 typów + własne pola) w rdzeniu TS i Kotlina, odczyt starych wpisów v2 jako login, ścisłe nagrobki, limit 64 KiB na blob, stronicowanie po bajtach, ścieżki `/p2p/v2/*` (stare `/p2p/v1/handshake|sync` → 410). Ekrany bez zmian: pokazują i edytują tylko loginy.

**Podejście:** model i parser w `core/src/p2p/entry.ts` oraz nowym `EntryV3.kt`; obie strony serializują wpis w jednej, stałej kolejności kluczy, więc wektory `v3.json` (stały nonce) dają ten sam blob. Synchronizacja dalej przenosi nieprzejrzyste bloby – host sprawdza tylko ich długość. Wtyczka i telefon mapują login v3 na dzisiejsze `{name, username, password}` i przy edycji zachowują pozostałe pola.

**Stos:** TypeScript (vitest), Kotlin JVM + kotlinx.serialization (JUnit 5), Compose bez zmian.

**Spec:** `docs/superpowers/specs/2026-11-07-typy-wpisow-design.md` (sekcje 3, 4, 7, 8 krok 1).

## Ograniczenia globalne

- AAD bez zmian: `passholder/v2/entry/<id>`; szyfr AES-256-GCM, blob = Base64(0x01 ‖ nonce 12 B ‖ szyfrogram ‖ tag 16 B).
- Kolejność kluczy przy zapisie (obie strony, identycznie): `v, type, name, note, fields, custom, hlc`; `fields` w kolejności z tabeli specu; element `custom`: `label, value, hidden`; `phones/emails`: `label, value`; `addresses`: `label, street, postalCode, city, country`; `hlc`: `ms, c, d`. JSON zwarty (bez spacji).
- `v` musi być liczbą całkowitą `3`. Wartości pól tekstowe, `hidden` boolean. Nieznany klucz na dowolnym poziomie → błąd `"Invalid entry payload"`.
- Stara treść v2: dokładnie klucze `{name, username, password, hlc}` (bez `v`) → login z `totp: ""`, `urls: []`, `androidApps: []`, `note: ""`, `custom: []`.
- Nagrobek: dokładnie `{hlc}`; inny klucz → `"Invalid tombstone payload"`.
- `MAX_ENTRY_BLOB_LENGTH = 65536` (znaki Base64). Długość bloba liczona bez szyfrowania: `4 * ceil((29 + utf8Bytes(json)) / 3)`.
- `MAX_BLOB_BYTES_PER_ROUND = 524288` (512 KiB, suma długości blobów w jednym żądaniu i w jednej odpowiedzi: `conflicts` + `changes`). **Odstępstwo od specu (768 KiB) – do akceptacji:** ciało żądania to Base64 ramek (×4/3), więc 768 KiB blobów daje ≥ 1 MiB i przekracza `MAX_BODY_BYTES`; 512 KiB + metadane 500 zmian ≈ 760 KB ciała.
- Limity liczby zmian bez zmian: 500/500.
- Komunikaty rdzenia po angielsku, tłumaczenie w aplikacjach: `"Entry too large"` → „Wpis jest za duży”; `"Phone app needs an update"` → „Zaktualizuj aplikację na telefonie”.
- Nazwy `LocalVaultV2`, `syncVaultV2`, `upsertEntryV2`, `encryptPayloadV2` zostają (v2 = schemat kryptograficzny i lokalny sejf), zmienia się typ danych.
- Po każdym zadaniu TS: `npm test`, `npm run typecheck`, `npm run build`. Po zadaniach Kotlina: `cd android && ./gradlew :core:test :app:testDebugUnitTest`. npm w kontenerze: `NO_PROXY=localhost npm ci --cafile=/root/.ccr/ca-bundle.crt`.

## Na co uważać przy przeglądzie

1. Edycja loginu w starym UI (wtyczka, telefon), gdy wpis ma już `urls`, `note`, `totp`, `custom` (np. z importu w kroku 4) – pola muszą przetrwać. Testy: zadanie 5 krok 1, zadanie 8 krok 1.
2. Lokalny sejf wtyczki zapisany przed aktualizacją (`entries[].data` w formacie v2) otwiera się i synchronizuje. Test: zadanie 5 krok 1.
3. Wpis innego typu (kontakt, karta…) przychodzący z synchronizacji nie psuje listy, nie trafia do loginów i nie jest liczony jako „nieczytelny”. Testy: zadanie 5 krok 1, zadanie 8 krok 1.
4. Odpowiedź, w której same `conflicts` przekraczają budżet bajtów (np. 20 konfliktów po 60 KiB) – host ucina, ustawia `more`, klient kończy w kolejnych rundach. Testy: zadanie 2 krok 1, zadanie 7 krok 1.
5. Limit 64 KiB liczony w bajtach UTF-8, nie w znakach (polskie litery, emoji). Testy: zadanie 1 krok 1, zadanie 6 krok 1.
